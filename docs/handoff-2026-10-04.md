### 3.1 H2 scoped (what "shelter accounts + admin" must mean)

The build-plan's 12 h line and "CRUD + CSV import + desktop layouts" is not a spec. This is,
pending his review of the types:

**Actors.** `super_admin` (Oleksii — provisions shelters, drives the verification FSM, sees
everything) and `shelter_admin` (member of exactly one shelter organisation; sees and edits
only that shelter's animals and the shelter's own profile fields that are safe to self-edit).

**Auth.** Better Auth 1.6.x with the `organization` plugin, as the ADR already decided. Email
+ password or magic link — **DEFAULT: magic link only** (volunteers, phones, no password
resets to support). Adopters stay on the anonymous session; nothing here touches it.

**Routes.** A route group inside `apps/web` (`/kabinet/...`), `noindex`, behind auth; desktop
layouts first-class (the only addition the build-plan already made). Mobile layout at the
same frames — a shelter volunteer *will* do this from a phone.

**Shelter admin can:** add an animal (all `Animal` fields, ≥1 photo via browser upload to
R2 through a presigned URL — H1's `sharp` variant pipeline runs server-side on the uploaded
key, not in the browser); edit; mark `reserved` / `adopted` (removes from feed, keeps
record); delete a draft; **confirm "still looking"** — a new `last_confirmed_at` column
distinct from `last_updated_at`, so commitment #7's freshness sentence can become
«востаннє підтверджено» honestly, and a typo fix never resets the date. Edit their contact
and donation link. Not: edit verification, legal entity, or exact address (super-admin
only, since those are what verification checked).

**Super admin can:** create a shelter org and invite its first admin; run the FSM
(`pending → under_review → verified / rejected`, `suspended`, `reinstate`, `re_review`)
with evidence items per `DEFAULT_VERIFICATION_POLICY`; edit anything; impersonate a shelter
view read-only for support. The operator script `onboard-shelter.ts` survives as the bulk
import path for a shelter that hands over a spreadsheet — **CSV import in the UI is cut
from H2** (DEFAULT); the script is the CSV import.

**Must-not (commitments register).** No engagement numbers of any kind on any shelter-facing
surface — no reveal counts, no "views", not even in the super-admin view of a shelter unless
clearly labelled as operator-only and never shown to the shelter (commitment #2). No
messaging between adopter and shelter (commitment #4). The `/prytulkam` §7/§9/§10
sentences («я внесу все сам», «напишіть, і я приберу», «відповідаю я») become false the day
self-serve ships — **H2's PR includes the rewritten Ukrainian for those three keys, written
by Oleksii** (commitment #6; Tier 1; put the three sentences in the copy inbox at Phase 0 of
H2 so he writes them while the code is built, not after).

**Launch-gate row folded in.** The create path wires `productionLocationPolicy` and adds
`LOCATION_HMAC_SECRET` to `RequiredProductionEnvSchema` in the same change (Part 5's first
gate). Verified against real Neon, not local, per the standing constraint.

**Tests that are non-negotiable for H2:** authorisation matrix (every procedure × every actor
× own/other shelter), as a table test — the same shape as the FSM transition table;
`implement(contract)` walk extended to the new router; `pick`-only public views unchanged

## 4. The loop, revised for throughput

The old loop serialised everything: build row → `pnpm check` (2m46s) → Opus reviewer runs the
suite again, mutates, returns → fix → re-review → commit → often a STOP that waits on
Oleksii → next row. A representative day produced three rows. Most of the cost was waiting,
not building. The changes below keep every check that caught a real bug and move the
waiting off the critical path.

### 4.1 Review is asynchronous and runs in parallel with the next row

After a row is committed (green `pnpm check`, as before), the builder **spawns
`opika-reviewer` in the background** (a background subagent — Claude Code runs it in its own
worktree; `.claude/worktrees/` already exists for this) against that commit range, and
**immediately starts the next row**. The reviewer writes its verdict to
`docs/reviews/<branch>/<short-sha>.md` (git-tracked, Tier 3) instead of returning it to the
builder's context.

The builder reads pending review files at three points only: when starting a row that
touches the same files as a reviewed row, before opening the PR, and when a review file says
`STOP`. Fixes for review findings are their own small commits ("review: <sha> — <finding>"),
re-reviewed by the same mechanism. Nothing waits for a reviewer to finish except the PR.

Two rows in flight at once is the limit (one building, one in review). If the reviewer is
slower than the builder for three rows running, the builder pauses for one review cycle
rather than piling up — the review is the thing that catches real bugs, so it must not fall
arbitrarily behind.

### 4.2 Review scope per tier is re-cut

- **Tier 1** (production data, migrations, secrets/cookies/HMAC/rate limits, Ukrainian copy,
  `/prytulkam` claims, asset licensing, anything a real shelter's data flows through):
  **unchanged — synchronous, blocking, Phase 0 questions to Oleksii first.** This tier is
  where the discipline earned its keep (the `db:seed` hostname exploit, the fabricated
  "verified" badges). Don't touch it.
- **Tier 2** (app code, layout, tests, harness, refactors): **asynchronous per row** as in
  §4.1. Reviewer does **not** re-run the full `pnpm check` — the commit's own green run is
  the evidence; the reviewer runs only the suites touching the diff plus its mutations.
  Mutation testing of a new guard/floor/assertion is **the builder's job, in the commit
  message** ("mutation: <what was broken> → <failure text>"); the reviewer spot-checks one
  per row and verifies the rest were done, not re-does them.
- **Tier 3** (docs, renames, formatting, config without runtime effect): no per-row review;
  one PR-level pass, as today.

Verdict vocabulary stays `PASS / PASS WITH NOTES / STOP`. A STOP on a Tier 2 row still means
"don't merge", never "don't commit" (the 2026-09-06 amendment stands).

### 4.4 Decisions stop blocking: one inbox, defaults, batch answers

`docs/decisions-pending-review.md` (752 lines, narrative, per-branch copies) is replaced by
`docs/decisions-inbox.md`, one table, **on `main` only**, append-only:

| ID | Date | Row | Question (one line) | Options | Default taken | Oleksii's answer | Status |

Rules:

- A **Tier 2 decision never blocks the builder.** Take the recommended default, write the row,
  continue. Oleksii answers in bulk when he reviews the PR; an override becomes a small
  follow-up commit.
- A **Tier 1 decision still blocks the merge** — but not the rest of the branch. The row is
  written, the work is committed, the builder moves to the next row that doesn't depend on
  it. Oleksii answers the batch, not one question at a time.
- **Ukrainian copy never blocks code.** New strings ship as `[COPY PENDING]` pinned by
  `copy-status.test.ts` (existing mechanism). Every copy need goes into the inbox with the
  English sense and the key name. Oleksii writes the Ukrainian in one sitting per block, and
  landing it is a Tier 3 commit (approved source → the string). The only copy that *does*
  block a merge is a `/prytulkam` commitment sentence (register rows), because a false
  sentence must never be live.
- Branches write new inbox rows to `docs/decisions-inbox/<branch>.md`; the PR merge appends
  them to the main table. No more hand-reconciled per-branch copies of a 750-line file.
- Decisions already resolved in the old file: leave the old file in place as history with a
  one-line pointer at the top ("superseded by decisions-inbox.md on 2026-10-04 — read-only").
  Don't migrate resolved entries.
