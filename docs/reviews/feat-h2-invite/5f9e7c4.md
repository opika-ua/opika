## FINDINGS (most severe first)

1. **[medium] email-senders.ts:57 vs email-provider.ts:255.** When the block status is `unknown`, the operator is told plain `sent`. The `BlockedStatus` comment says "Not knowable: say so, never guess". `sendChecked` then folds `unknown` (lookup timeout, 401, more than 500 blocked contacts) into `{kind:"sent"}`, and the contract has no way to carry it.
   *Failure scenario:* the block list holds 501 entries and the invitee is the 501st. The result is `list_too_long`, then `sent`. Brevo drops the email and the operator's screen says it was sent. That is exactly the silent stop IN-E7 exists to surface.
   IN-E11(2) records "send anyway" but not that the uncertainty disappears from the operator's view. *Fix:* either `sent` gets an optional `blockCheck: "unknown"` (a contract change, then re-review), or IN-E11 records the loss explicitly and the comment at :255 is corrected. Sending anyway stays reasonable either way.
2. **[low] email-provider.ts `blockedStatusOf`: worst-case latency is serial.** Up to 5 GETs at a 10s timeout each, plus the send, comes to about 60s. Operator invites wait for that inside the request. Sign-in pays it inside `after()`, which counts against the function's maxDuration. I verified neither against Vercel limits. Put it in the inbox, or cut the per-page timeout.
3. **[low] email-message.ts `looksLikeUrl`: the bare-domain check only matches at the start of the label.** «Перейти на opika.org.ua» passes, and that is the domain-vs-href mismatch IN-E8 forbids. Labels come from the copy sheet, so the exposure is small. Search for the pattern anywhere in the label (`\b[^\s]+\.[a-z]{2,}\b`).
4. **[note] IN-E7's "the invite UI shows the failure" test.** It is deferred to the screens PR, and that is recorded in IN-E7's Built text. Carry it as a named row so it isn't lost. IN-E9 is correctly left open as Tier 1 and merge-blocking.
