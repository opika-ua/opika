## Findings (most severe first)

1. **[medium] `packages/db/src/repos/kabinet-invite-token-repo.ts:136-138` — the three EXISTS flags
   are normalised fail-open (`=== true`), and step 17 only exercises them as false.** If a driver ever
   returned `'t'`, `operator`/`hasPassword`/`member` would read false and the operator's or a
   password holder's link would become usable. Today it holds: drizzle 0.45.2's neon-http
   (`driver.js:24-32`) overrides date/interval parsers, not bool (OID 16), so Neon returns booleans;
   I read that, I didn't run it. But this is the driver-dependent part of PW-2's new SQL and the smoke
   can't catch it: its second POST is 410 because the row was consumed, not because `hasPassword` is
   true. Fix: fail closed (`row.operator !== false`, etc.), or add one step-17 check that a
   has-password (or operator) link reads `unusable` over neon-http.
2. **[medium-low] F8 on the POST's other statements is claimed but untested.** Mutation: router
   `accept: invitationAccepter(context.db, …)` plus the accepter logging `String(error)`. Every builder
   suite (invite*, clean-query-errors, auth-log, password-flows, registry: 249 tests) stays green while
   the address reaches the log. Only my forced accept failure catches it. Each layer saves it alone
   today (M5, M6 each survive), so no live leak. Add forced-failure tests for consume and the accept
   on the procedure, like `invite-tokens.test.ts`'s lookup case. Also, `inviteTokensOf` on the raw handle
   is caught only by the page test. The registry's `issue` has no cleaned-error test (mine passes).
3. **[low] `invite-password-flows.test.ts:342` "two submissions at once" runs on a `max: 1` connection,**
   so Postgres never sees two concurrent DELETEs. It catches "consume without deleting" only by
   interleaving. Behaviour verified by my two-connection forced test (below); worth adopting it.
4. **[low] `invite-password.ts:225-231` crash window.** `createAccount` then `updateUser(emailVerified)`:
   a failure between the two leaves a password, an unverified address, a used link, and a resend that
   reads `hasPassword` → unusable. The automatic accept needs a verified address, so only a magic-link
   sign-in recovers. Marking verified first closes it: a failure after that leaves no password, and a
   resend works.
5. **[low] The unusable page leaves `?zaproshennia=` in the address bar and history.** Only
   `SetPasswordCard` calls replaceState. In every unusable case I traced the token is dead, and
   analytics strips it. His Q3 reads as token removal generally, so the same one-liner on
   `InviteUnusableCard` would match it.
6. **[low] `invite-landing-get.test.ts:183` (one identical page) has no has-password, member or
