FINDINGS (most severe first; none blocking)
1. [Note] `GalleryControlBlock.tsx:66-72,137-139` - un-clipping depends only on `transitionend`,
   with no fallback timer.
   Failure scenario: the visitor reopens the row, then crosses below 1024px (a window resize or
   browser zoom) within the 300ms opening transition, then comes back above 1024px. The row is
   open with `expanded` still false, so the dropdown options are invisible again (the originally
   reported bug) until the row is closed and reopened.
   Evidence: scratch harness case S4 red with viewport ratio 0; the S5 control (same resize after
   the transition has finished) is green.
   The repo already has this pattern elsewhere: `use-swipe-gesture.ts`'s `whenTransitionSettles`
   adds a fallback timer because "transitionend is not guaranteed to fire." Same backstop would
   close this gap.
2. [Note, tests] `gallery-filters.harness.ts:104` (РОЗМІР → Великий) passed with the original bug
   put back - Playwright's click scrolled the `overflow-hidden` wrapper to reach the option
   (scrollTop 114), so "harness 155 passed" said nothing about this specific fix. Adding
   `expect(getByRole("link",{name:"Великий"})).toBeInViewport()` before that click goes red on
   the bug and green at this SHA; the new unit tests are className checks on happy-dom with
   synthetic events, pinning the state logic but not what a real browser does with the popup.
3. [Note] The commit body pastes no `pnpm check` output - it summarises separately run steps
   (tests scoped to `@opika/web`, lint on two files only).
4. [Note, minor] In the test file, `vi.unstubAllGlobals()` is the last line of the reduced-motion
   test, so a failing assertion above it would leak the stub; use try/finally or afterEach. The
   test comment calls the class "an inline style"; it is a class.
5. [Note, minor] `event.target === event.currentTarget` would harden the `onTransitionEnd` guard.
   Not needed today - the only `grid-template-rows` transition in `apps/web/src` is this row.
