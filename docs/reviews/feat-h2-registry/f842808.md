## Findings

1. **[medium] `check-migration-hashes.ts` `compareHashes`/`main`: if 0011 is regenerated after a rehearsal, the result is `not run` and exit 0. It is never reported as `MISMATCH`.** The check matches by `when`, and `drizzle-kit generate` assigns a new `when` when 0011 is regenerated. This happened today in the working tree: `1791881894167` became `1791884035811`, and `lovely_black_knight` became `amazing_young_avengers`.
   - Failure scenario: the rehearsal branch ran the old 0011, and the committed file is the new 0011. The tool prints `not run  0011_…` and ignores the old row, which matches no journal entry. It then exits 0. That is the exact drift RS-R1 exists to catch ("a branch can't have run a different 0011"). A later `db:migrate` on that branch would also apply the new 0011 on top of the old one, because B > A.
   - The checklist line (`h2-next-prs.md`: "prints `match` for 0011") saves a careful human reader, but the exit code tells a script the opposite.
   - Fix: report recorded rows that match no journal `when` as `unknown` and exit 1. Consider exiting non-zero on `not_applied` when a later entry is applied. Add a test that sets 0011's `when` to a fresh value and expects a non-zero result.
2. **[low] The commit's `mutation:` line describes the test fixture, not a mutation of the code, and it has no failure text.** "0011's committed hash replaced → … asserts exactly that one" is what test 2 already does. No line shows a guard being broken and turning red. The spot-check above covers the hashing path. Finding 1 shows the mutation that mattered (a changed `when`) was never tried.
3. **[low] `test/check-migration-hashes.test.ts:37` asserts the literal tag `0011_lovely_black_knight`.** While 0011 is allowed to grow, that tag fails on every regeneration. The builder's uncommitted `startsWith("0011_")` change addresses this.
