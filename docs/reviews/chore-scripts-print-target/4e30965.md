1. [low] packages/db/src/migrate.ts:19: the comment "After the guard (a refused target gets nothing but the refusal)" is a documented invariant that no test checks. I moved the print above `assertProductionWriteAllowed` and every test stayed green. The refusal tests only check stderr.

2. [low] prod-guard.ts `databaseTargetOf`: with a postgres-js multihost URL the label is wrong. Example: `postgres://u:p@ep-a-pooler.x.neon.tech,localhost/db` prints "remote host ep-a-pooler.x.neon.tech,localhost (not a Neon endpoint)", but postgres-js connects to the Neon host first. The guard still catches it, because `computeOf` reads `ep-a`. Separately, `postgres:///opika` prints "remote host  (not a Neon endpoint)" with an empty host, while the driver actually goes to PGHOST or localhost. Nothing leaks in either case, but the label is false, and its whole purpose is to be proof. Either return `unparseable` (or a new "ambiguous" kind) for a host that contains `,` or is empty, or record it as a follow-up.
3. [note] prod-guard.ts:83: the doc comment says the check is the "same test as client.ts's isNeonHost". It isn't quite. The helper strips a trailing dot first, so for `x.neon.tech.` it says Neon while `isNeonHost` picks postgres-js. The destination is still Neon, so the label holds, but the comment overstates the match.
4. [scope] admin.ts and verify-locations.ts were switched as well, which Oleksii did not ask for. The change is harmless and consistent. But the commit leaves seed.ts out "per scope" while widening scope elsewhere.
   **seed.ts judgement:** don't fix it in this commit. Line 1453 runs after both guards. Neon puts the password in the userinfo, which the regex masks. What it leaves visible is the role name and the query string, and neither holds a secret in Neon's own URLs. It's a real weakness (a raw `:` in a password, or a `?password=` URL), but it comes from an earlier change, and the fix (`databaseTargetLine`) is a one-line follow-up row.
