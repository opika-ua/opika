## FINDINGS (most severe first)

1. **[Note] `clean-query-errors.ts:95-122`: transactions aren't really covered.**
   - Probe 1: an `APIError` or `tx.rollback()` thrown inside `clean.transaction(cb)` reaches the
     caller as `CleanedQueryError` (`became CleanedQueryError/APIError | rollback: CleanedQueryError`).
   - Probe 2: a statement on `tx` fails **raw** inside the callback (address, `params:`, SQL); it is
     cleaned only once it escapes.
   - Mutation R1 (`transaction` left unwrapped) passes 26/26, so no test pins this path.
   - It is latent: no production transaction runs on the cleaned handle, and neon-http has none.
   - Fix: rethrow non-query errors unchanged, or document the limit, and add one test.
2. **[Note] `clean-query-errors.test.ts`, the Better Auth 23505 case.** Its "raw" side is not raw.
   `authOver` goes through `createKabinetAuth`, which always wraps the handle (`auth.ts:221`). There
   is no risk, because Better Auth reads no SQLSTATE. Fix: build the raw side with `drizzleAdapter`
   directly, or reword the claim.
3. **[Note] `auth-log.ts:16-24`: identifiers with underscores are masked as tokens.** Snake_case runs
   of 20 or more characters become «•••» in free text: `auth_user_email_unique`,
   `kabinet_member_one_shelter_idx`, `INTERNAL_SERVER_ERROR` (probe). This over-masks; it leaks
   nothing. Ukrainian words, short English words, SQLSTATEs, `%40` addresses, `Params:`/`PARAMS:`
   and a 32-character session token all behave correctly.
4. **[Note] `clean-query-errors.ts:44`: any name made only of letters survives.** An error named
   `mykola` keeps that name. No library sets an error's name from data.
5. **[Residual, outside this diff]** Kabinet pages and server actions still query `getDb()` raw. For
   example, `invitationOf(id)` in `vkhid` and `hasPassword(userId)`. A throw there reaches Next's log
   with Drizzle's `params:`, which hold ids, not a token, address or password. This is a follow-up
   row, not this PR's.

## What a /kabinet page load does during an outage

`proxy.ts` calls `kabinetPageLoadAllowed`, which calls `kabinetPageUserId`. That throws a
`CleanedQueryError`, so the request fails with a 500. Next logs that cleaned error: its name, its code
when it is a SQLSTATE, and stack frames. The outage is never read as "signed out" (R4 proves the test
catches that). `kabinetIdentityOf` behaves the same way in the pages and the RPC route.
