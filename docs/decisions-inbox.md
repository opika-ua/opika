# Decisions inbox

One table, on `main` only, append-only. Replaces `docs/decisions-pending-review.md`'s
per-branch narrative copies for every decision made from 2026-10-04 onward — see
`docs/handoff-2026-10-04.md` §4.4 and `CLAUDE.md`'s working loop, "Decisions stop blocking."

`docs/decisions-pending-review.md` is superseded and kept as read-only history; its own entries
are not migrated here.

## How this file is used

- A **Tier 2 decision never blocks the builder.** Take the recommended default, add a row here,
  continue. Oleksii answers in bulk when he reviews the PR; an override becomes a small
  follow-up commit, and the row's **Status** column is updated to `overridden` with a pointer to
  that commit. **This is not the STOP list** (`CLAUDE.md`'s "Stop and ask, regardless of what the
  reviewer said") — an ambiguous design with no mock, a new or changed user-facing claim, and the
  rest of that list still stop and wait, never take a default, no matter which tier the
  surrounding code is.
- A **Tier 1 decision still blocks the merge** — but not the rest of the branch. Add the row,
  commit the work, move to the next row that doesn't depend on it.
- **Ukrainian copy never blocks code.** New strings ship as `[COPY PENDING]`, pinned by
  `copy-status.test.ts`; the English sense and key name go in the **Question**/**Options**
  columns here. The only copy that *does* block a merge is a `/prytulkam` commitment sentence
  (`docs/standing-constraints.md`'s register), because a false sentence must never be live.
- **Branches write new rows to `docs/decisions-inbox/<branch>.md`** (same columns, one table, no
  header boilerplate needed beyond the column row) rather than editing this file directly — this
  file lives on `main` only. **Appending the branch's rows to the table below is part of merging
  the PR** — done at the same time as deleting the branch's own `docs/decisions-inbox/<branch>.md`.
  (Written when Oleksii was the one who merged every PR, hence did the fold himself; since the
  2026-10-21/2026-10-23 "Who does what" change in `CLAUDE.md`, the local agent is the one that
  merges, so it does the fold too — a mechanical consequence of that change, recorded as a
  builder's decision under "Decisions taken" in PR #189's body, his to overturn, not assumed
  settled.) A branch's rows are not "in"
  the inbox for his bulk-answer pass until that append has happened; say so explicitly in the PR
  body rather than assuming it's automatic.
- **Status** is one of: `open` (Tier 1, awaiting Oleksii), `default-taken` (Tier 2, no response
  needed unless he overrides), `answered` (he responded — see his answer column), `overridden`
  (he changed a default-taken row after the fact).

## KH-F1 runbook step (operator, the production branch, Neon SQL editor)

The single text to run: the coordinator's proposal (chat, 2026-10-14) with Oleksii's amendments
(hex password, `auth_account` in the REVOKE, a verification that covers the three revoked
tables). Create the role with SQL, not the console's Roles page, so it is not a `neon_superuser`
member. Database `neondb`.

```sql
-- Password: hex, never base64 ('/', '+', '=' break the connection URL).
-- Generate locally: openssl rand -hex 32. Paste it in place of <hex>; never into chat.
-- Afterwards, delete this CREATE ROLE entry from the SQL editor's History (it stores the password).
CREATE ROLE opika_readonly WITH LOGIN PASSWORD '<hex>';
ALTER ROLE opika_readonly SET default_transaction_read_only = on;
GRANT CONNECT ON DATABASE neondb TO opika_readonly;
GRANT USAGE ON SCHEMA public TO opika_readonly;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO opika_readonly;
GRANT USAGE ON SCHEMA drizzle TO opika_readonly;
GRANT SELECT ON drizzle.__drizzle_migrations TO opika_readonly;
REVOKE SELECT ON auth_session, auth_verification, auth_account FROM opika_readonly;

-- Verification 1. Expected: can_write false on every row; can_select false on exactly
-- auth_account, auth_session and auth_verification, true on every other table.
SELECT t.table_name,
       has_table_privilege('opika_readonly', format('public.%I', t.table_name), 'SELECT') AS can_select,
       has_table_privilege('opika_readonly', format('public.%I', t.table_name),
                           'INSERT, UPDATE, DELETE, TRUNCATE') AS can_write
FROM information_schema.tables t
WHERE t.table_schema = 'public'
ORDER BY t.table_name;
-- Verification 2. Expected: true (the migration journal is readable).
SELECT has_table_privilege('opika_readonly', 'drizzle.__drizzle_migrations', 'SELECT');
-- Verification 3. Expected: one row, every column false.
SELECT rolsuper, rolcreaterole, rolcreatedb, rolreplication, rolbypassrls
FROM pg_roles WHERE rolname = 'opika_readonly';
```

Decided (Oleksii, 2026-10-14, verbatim, relayed by the coordinating session): "KH-F1: drop
ALTER DEFAULT PRIVILEGES; new tables stay unreadable until granted by hand. Adopter sessions
table (hashes only) stays readable: fine." The SQL above no longer has that line: a table a
later migration adds is unreadable to this role until granted by hand, so a check reading it
fails loudly rather than silently gaining access. Child branches created afterwards inherit
`opika_readonly` and its password, like any role (see KH-S1's addendum).
