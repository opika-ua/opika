Resolved. One real, unprompted finding surfaced during implementation, not part of the original STOP: the Vercel Storage marketplace integration names the injected credentials `KV_REST_API_URL`/`KV_REST_API_TOKEN` (Vercel's legacy "Vercel KV" naming, kept for `@vercel/kv` backward compatibility) — **not** `UPSTASH_REDIS_REST_URL`/`UPSTASH_REDIS_REST_TOKEN`, which the original implementation (written before provisioning) assumed and which this real deployment never actually had set. `rate-limit.ts` and `env.ts` both now accept either naming pair (`KV_REST_API_*` preferred, `UPSTASH_REDIS_REST_*` as a fallback for whoever connects the store a different way), matching a complete pair as a unit rather than cross-matching fields between the two naming conventions — a second real bug this project's own test suite caught during the fix (an earlier version resolved the URL and token independently, which could silently pair a URL from one naming scheme with a token from the other).

A third finding, from a second Tier 1 review round against the real library and a real (deliberately unreachable) endpoint rather than the first round's reasoning alone: the first RL-1 implementation left the SDK's own `timeout` branch returning `false` with no log line, and the written account of "DNS failure/connection refused reject and get caught" was wrong against the real client — those cases were actually resolving through the *timeout* path instead, because `@upstash/redis`'s own default retry behavior (5 retries, exponential backoff) delayed the rejection past the 1-second bound. Fixed by disabling the client's own retries (`retry: { retries: 0 }`, so a real failure now rejects fast and is caught/logged as originally intended) and by logging the timeout branch too.
