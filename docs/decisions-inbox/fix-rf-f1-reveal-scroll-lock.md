Confirmed by forcing it deterministically: a `MutationObserver` reading `document.body.style.overflow` at the instant the `reveal-dialog` node first appears in the DOM saw `""` under the passive `useEffect` and `"hidden"` under `useLayoutEffect`, for the same render. A passive effect runs on the browser's own post-paint schedule, so between the dialog's own DOM insertion and the effect firing there is a real — if usually brief — frame where the overlay is visible and the page behind it can still scroll; a layout effect runs synchronously in the same commit that inserts the dialog, before anything paints, so that frame never exists at all, in the test or in a real browser. This is a strictly better fix than `waitFor`: it removes the underlying race rather than giving the test more patience with it, and the test's own assertion (checked right after `findByTestId`) keeps testing real, committed state rather than an eventually-consistent one. | — | fixed in this branch; see `apps/web/src/features/reveal/ContactRevealDialog.tsx` |
